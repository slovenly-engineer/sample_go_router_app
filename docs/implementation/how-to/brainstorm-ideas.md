# 新機能アイデア出しガイド

## 概要

このガイドでは、新機能や機能改善のアイデアを出す際の手順を説明します。
brainstormサブエージェントが自動的にこのプロセスを実行しますが、手動で実行する場合にも参照できます。

## アイデア出しプロセス

### Phase 1: 文脈理解と初期アイデア生成

#### 目的
- 既存コードベースの理解
- 制約条件の明確化
- プロジェクト固有の文脈を踏まえた初期アイデアの生成

#### 手順

1. **関連機能の探索**
   ```bash
   # 関連する機能ディレクトリを検索
   find lib/features -type d -name "*[keyword]*"

   # 関連するコードを検索
   grep -r "keyword" lib/features/
   ```

2. **アーキテクチャ原則の確認**
   - `docs/common/architecture-principles.md` を読む
   - Feature-basedディレクトリ構造を理解
   - Riverpod状態管理パターンを確認
   - go_routerナビゲーション設計を理解

3. **コーディング規約の確認**
   - `docs/common/coding-conventions.md` を読む
   - 命名規則（スネークケース、パスカルケース）
   - ファイル構成のパターン
   - コメントとドキュメンテーションのルール

4. **制約条件の洗い出し**

   **技術的制約**:
   - Flutter/Dartのバージョン
   - 使用可能なパッケージ
   - プラットフォーム制約（iOS/Android/Web/Desktop）
   - パフォーマンス要件

   **ビジネス的制約**:
   - 開発期間
   - リソース（人員、予算）
   - 優先度

   **アーキテクチャ制約**:
   - 既存のアーキテクチャパターンとの整合性
   - 依存関係の管理
   - 既存機能への影響

5. **初期アイデアの生成**

   以下の観点から3-5個のアイデアを生成：

   - **既存機能の改善**: 現在の実装を改良
   - **新規機能の追加**: 全く新しい機能を追加
   - **UX改善**: ユーザー体験の向上
   - **パフォーマンス最適化**: 速度やメモリ使用量の改善
   - **保守性向上**: コードの整理やリファクタリング

   各アイデアには以下を含める：
   ```markdown
   ### [アイデア名]
   - **概要**: [1-2文で説明]
   - **影響範囲**: [変更が必要なファイル/機能]
   - **実装複雑度**: Low/Medium/High
   - **想定される課題**: [技術的な懸念点]
   ```

### Phase 2: アイデア拡張と多様化（Gemini brainstorm）

#### 目的
- 外部視点を取り入れた多様なアイデアの生成
- 創造的なアプローチの探索
- アイデアの実現可能性分析

#### 手順

1. **Gemini brainstormの準備**

   以下の情報を整理：
   - Phase 1で生成した初期アイデア
   - ユーザー要件（元のリクエスト）
   - 制約条件（技術的・ビジネス的）
   - 既存コードの文脈

2. **Gemini brainstormの実行**

   ```
   mcp__gemini-cli__brainstorm を呼び出す:

   prompt: |
     Flutter/Dartアプリケーションの[機能名]について、以下のアイデアを発展させてください。

     初期アイデア:
     1. [アイデア1]
     2. [アイデア2]
     3. [アイデア3]

     ユーザー要件:
     - [要件1]
     - [要件2]

     既存の実装:
     - [既存機能の概要]

   domain: "software"
   methodology: "divergent" または "design-thinking"
   constraints: |
     - Flutter/Dart環境
     - [その他の制約]
   existingContext: |
     - 現在の実装状況
     - 過去の試み
   ideaCount: 12-15
   includeAnalysis: true
   ```

3. **結果の精査**

   生成されたアイデアを以下の基準で評価：
   - **関連性**: プロジェクトの目的と合致しているか
   - **実現可能性**: 技術的に実装可能か
   - **独自性**: 既存の実装と重複していないか
   - **価値**: ユーザーにとって有用か

   評価後、有望なアイデア10個程度に絞り込む。

4. **アイデアのグルーピング**

   類似したアイデアをまとめる：
   - **UI/UX改善系**
   - **機能拡張系**
   - **パフォーマンス最適化系**
   - **保守性向上系**

### Phase 3: 技術検証（必要時）

#### 目的
- 技術的な実現可能性の確認
- リスクの特定と対策の検討
- 最適な実装方法の選定

#### 実施すべき状況

以下のいずれかに該当する場合に実施：

1. **新しいパッケージの導入が必要**
   - pub.devでの検索
   - パッケージの評価（メンテナンス状況、互換性）
   - ライセンス確認

2. **パフォーマンス影響が懸念される**
   - メモリ使用量の増加
   - レンダリング速度への影響
   - バッテリー消費

3. **セキュリティリスクがある**
   - 個人情報の扱い
   - 認証・認可の仕組み
   - データの暗号化

4. **プラットフォーム固有の制約**
   - iOS/Androidのネイティブ機能
   - Web対応の可否
   - Desktopプラットフォームの制限

#### 検証方法

**方法1: Gemini ask-geminiを使用**

```
mcp__gemini-cli__ask-gemini を呼び出す:

prompt: |
  Flutterアプリで[技術要素]を実装する際の以下の点を教えてください：
  1. 実現可能性
  2. パフォーマンス影響
  3. セキュリティ考慮事項
  4. 推奨される実装方法
  5. 注意すべき落とし穴

changeMode: false
```

**方法2: Codexを使用**

より詳細な技術検証が必要な場合：
- プロトタイプコードの生成
- パフォーマンステストの実施
- セキュリティ監査

**方法3: 既存コードベースの参照**

類似機能が既に実装されている場合：
```bash
# 類似実装を検索
grep -r "similar_feature" lib/features/

# 使用されているパッケージを確認
cat pubspec.yaml
```

#### 検証結果のまとめ

```markdown
### 技術検証結果

#### 検証項目: [パッケージ名/技術要素]

**実現可能性**: 高/中/低
- [理由]

**パフォーマンス影響**:
- メモリ: [評価]
- 速度: [評価]

**セキュリティ**:
- [懸念点と対策]

**推奨実装方法**:
- [具体的な実装アプローチ]

**リスク**:
- [リスクと軽減策]
```

### Phase 4: 統合・評価・決定

#### 目的
- 全アイデアの総合評価
- 最適なアイデアの選定
- 次のステップの明確化

#### 評価基準

各アイデアを以下の6つの観点で評価（100点満点）：

##### 1. アーキテクチャ適合性（20点）

**評価ポイント**:
- 既存のアーキテクチャパターンに沿っているか
- Feature-basedディレクトリ構造に適合するか
- Riverpod状態管理パターンを正しく使用しているか
- go_routerナビゲーション設計に合致するか

**配点例**:
- 完全に適合: 18-20点
- おおむね適合（小規模な調整が必要）: 14-17点
- 部分的に適合（中規模な調整が必要）: 10-13点
- 適合しない（大幅な調整が必要）: 0-9点

##### 2. 実装コスト（15点）

**評価ポイント**:
- 必要な開発工数
- 変更するファイル数
- 新規パッケージの導入数
- テストの実装範囲

**配点例**:
- 非常に低コスト（1-2日、2-5ファイル）: 13-15点
- 低コスト（3-5日、6-10ファイル）: 10-12点
- 中コスト（1-2週、11-20ファイル）: 7-9点
- 高コスト（2週以上、20ファイル以上）: 0-6点

##### 3. ユーザー価値（25点）

**評価ポイント**:
- ユーザーの課題解決度
- UX改善の度合い
- 機能の有用性
- ユーザーへのインパクト

**配点例**:
- 非常に高い価値: 21-25点
- 高い価値: 16-20点
- 中程度の価値: 11-15点
- 低い価値: 0-10点

##### 4. 保守性（15点）

**評価ポイント**:
- コードの理解しやすさ
- テストのしやすさ
- 変更への対応力
- ドキュメンテーションの容易さ

**配点例**:
- 非常に高い保守性: 13-15点
- 高い保守性: 10-12点
- 中程度の保守性: 7-9点
- 低い保守性: 0-6点

##### 5. 拡張性（15点）

**評価ポイント**:
- 将来的な機能追加の余地
- スケーラビリティ
- 他機能との連携可能性
- 再利用性

**配点例**:
- 非常に高い拡張性: 13-15点
- 高い拡張性: 10-12点
- 中程度の拡張性: 7-9点
- 低い拡張性: 0-6点

##### 6. 技術的リスク（10点）

**評価ポイント**:
- 実現可能性の確実性
- 未知の技術要素
- プラットフォーム依存の課題
- 潜在的なバグの可能性

**配点例**:
- 非常に低リスク: 9-10点
- 低リスク: 7-8点
- 中程度のリスク: 5-6点
- 高リスク: 0-4点

#### 評価テンプレート

```markdown
### [アイデア名]

**総合スコア**: XX/100

#### 詳細評価

**1. アーキテクチャ適合性**: XX/20
- [評価理由]
- [具体的な整合性/不整合点]

**2. 実装コスト**: XX/15
- 工数見積もり: [X日/週]
- 変更ファイル数: [Xファイル]
- 新規パッケージ: [あり/なし]

**3. ユーザー価値**: XX/25
- [どのような価値を提供するか]
- [ユーザー体験の改善点]

**4. 保守性**: XX/15
- [保守のしやすさ]
- [テスト戦略]

**5. 拡張性**: XX/15
- [将来的な拡張の可能性]
- [再利用性]

**6. 技術的リスク**: XX/10
- [リスク要因]
- [軽減策]
```

#### 最終選定

1. **スコアリング**
   - 全アイデアを評価
   - 上位3-5案を選定

2. **バランス確認**
   - ユーザー価値と実装コストのバランス
   - 短期的価値と長期的価値のバランス
   - リスクとリターンのバランス

3. **推奨順位の決定**
   ```markdown
   ### 推奨順位

   1. **[アイデア名]** (スコア: XX/100)
      - メリット: [...]
      - 推奨理由: [...]

   2. **[アイデア名]** (スコア: XX/100)
      - メリット: [...]
      - 推奨理由: [...]

   3. **[アイデア名]** (スコア: XX/100)
      - メリット: [...]
      - 推奨理由: [...]
   ```

## 次のステップ

### 1. ADRの作成

選定されたアイデアをADR（Architecture Decision Record）として文書化：

```bash
# ADRファイルを作成
docs/specification/architecture/decisions/XXXX-[feature-name].md
```

ADRには以下を含める：
- 概要
- ユーザー要件
- アーキテクチャ判断
- 実装ファイル一覧
- 詳細設計
- プラットフォーム設定
- 実装順序
- 既存コードへの影響
- テスト計画
- 将来の拡張性
- 代替案
- 参考資料

### 2. 詳細設計

Plan Modeで詳細な実装計画を作成：

```
Use the Plan agent to create a detailed implementation plan for [feature]
```

### 3. プロトタイプ（必要に応じて）

技術的な不確実性が高い場合、小規模なプロトタイプを作成：

```bash
# プロトタイプディレクトリ
prototype/[feature-name]/
```

## ベストプラクティス

### DO（推奨）

- ✅ 既存コードベースを十分に理解してからアイデアを生成する
- ✅ Gemini brainstormを活用して多様な視点を取り入れる
- ✅ 技術的な不確実性がある場合は必ず検証する
- ✅ 評価基準を一貫して適用する
- ✅ ユーザー価値を最優先に考える
- ✅ 実装コストを現実的に見積もる
- ✅ アイデアの根拠を明確にする
- ✅ 代替案も検討する

### DON'T（非推奨）

- ❌ 既存コードを読まずにアイデアを生成する
- ❌ 制約条件を無視した理想論を展開する
- ❌ 評価を主観的に行う
- ❌ 技術的リスクを軽視する
- ❌ ユーザー価値よりも技術的面白さを優先する
- ❌ 実装コストを過小評価する
- ❌ Phase 2（Gemini brainstorm）をスキップする

## トラブルシューティング

### アイデアが出ない

**原因**: 制約が多すぎる、または問題の理解が不十分

**対策**:
1. 制約を一時的に緩めてブレインストーミング
2. 既存の実装をもう一度詳しく読む
3. ユーザー要件を再確認する
4. 類似プロジェクトを参考にする

### アイデアが多すぎて絞り込めない

**原因**: 評価基準が曖昧

**対策**:
1. 評価基準を明確にする
2. 各観点のウェイトを調整する
3. ユーザーに優先度を確認する（AskUserQuestion）
4. 実装コストとユーザー価値の2軸で整理

### 技術的実現可能性が不明

**原因**: 新しい技術要素、情報不足

**対策**:
1. Gemini ask-geminiで調査
2. Codexでプロトタイプ作成
3. 公式ドキュメントを確認
4. 小規模な検証プログラムを作成

### Gemini brainstormの結果が期待外れ

**原因**: プロンプトが不明確、制約が不適切

**対策**:
1. プロンプトをより具体的にする
2. 既存コードの文脈を詳しく説明する
3. methodologyを変更（divergent → design-thinking）
4. ideaCountを調整
5. 複数回実行して結果を比較
