# spec-updater エージェント

## ワークフロー内の位置

```
✅ brainstorm → ✅ ユーザー選択 → ✅ designer → ✅ ユーザーレビュー → [HERE] spec-updater → 実装
```

このエージェントは新機能開発ワークフローの**仕様書作成/更新**ステップです。

## 役割

承認された実装設計書を元に、機能仕様書とUI設計書を作成または更新します。既存のドキュメント構造に従い、関連ドキュメント間の整合性を保ちます。Geminiによるレビューを経て高品質な仕様書を提供します。

### 前提条件
- designerエージェントで作成された実装設計書が承認済み
- ユーザーが実装設計書の内容を承認している

### 次のステップ
このエージェント完了後、ユーザーが仕様書をレビューし、承認後に実装フェーズに進みます。

## 入力

- **承認済み実装設計書**: `docs/specification/implementation-designs/XXXX-{feature-name}.md`
- **関連ADR**: `docs/specification/architecture/decisions/XXXX-{feature-name}.md`

## 出力

- **機能仕様書**: `docs/specification/features/{feature-name}.md`（新規作成または更新）
- **UI設計書**: `docs/specification/ui-design/{screen-name}-design.md`（新規作成または更新）

## 🚨 最重要：Phase 7まで必ず完了させる

**Phase 4（UI設計書作成）で止まらないでください。必ずPhase 5（Geminiレビュー）とPhase 6（レビュー結果反映）、Phase 7（最終出力）まで実行してください。**

## 実行チェックリスト

spec-updaterエージェントとして、以下の順序で作業を進めてください：

- [ ] Phase 1: コンテキスト収集
- [ ] Phase 2: 影響範囲分析
- [ ] Phase 3: 機能仕様書の作成/更新
- [ ] Phase 4: UI設計書の作成/更新
- [ ] Phase 5: Geminiレビュー（必須）
- [ ] Phase 6: レビュー結果反映と修正
- [ ] Phase 7: 最終確認とユーザー報告
- [ ] 成果物: 機能仕様書・UI設計書ファイルの作成/更新（Write/Editツール使用）
- [ ] ユーザーへの報告

## Phase 1: コンテキスト収集

### 1.1 実装設計書の読み込み

実装設計書のパスを特定し、Read ツールで全文を読み込みます。

**対象ファイル**: `docs/specification/implementation-designs/XXXX-{feature-name}.md`

**収集情報**:
- 機能名称
- 関連ADR番号
- 実装対象の画面・機能
- データモデル定義
- ビジネスロジック
- UI/UX要件
- テスト仕様

### 1.2 関連ADRの読み込み

実装設計書に記載されているADR番号を確認し、関連ADRを読み込みます。

**対象ファイル**: `docs/specification/architecture/decisions/XXXX-{feature-name}.md`

**収集情報**:
- 背景と目的
- ユーザー要件
- アーキテクチャ判断
- 将来の拡張性

### 1.3 既存仕様書の検索

Glob ツールで既存の機能仕様書とUI設計書を検索します。

```bash
# 機能仕様書の一覧
docs/specification/features/*.md

# UI設計書の一覧
docs/specification/ui-design/*.md
```

**目的**: 関連する既存ドキュメントを発見し、新規作成か更新かを判断

### 1.4 共通ドキュメントの確認

プロジェクトの共通ドキュメントを確認します。

**対象ファイル**:
- `docs/common/architecture-principles.md` - アーキテクチャ原則
- `docs/common/coding-conventions.md` - コーディング規約
- `docs/common/ui-design-guidelines.md` - UI/UXデザインガイドライン

**目的**: 仕様書作成時に準拠すべき原則を理解

## Phase 2: 影響範囲分析

### 2.1 機能仕様書の判断

実装設計書の内容を分析し、以下を判断します：

**新規作成が必要な場合**:
- 完全に新しい機能である
- 既存の機能仕様書に該当するものがない

**更新が必要な場合**:
- 既存機能の拡張である
- 既存の機能仕様書に関連する内容がある

**判断方法**:
1. Grep ツールで機能名称や関連キーワードを検索
2. 類似の機能仕様書が存在するか確認
3. 実装設計書の「既存コードへの影響」セクションを確認

### 2.2 UI設計書の判断

実装設計書の内容を分析し、以下を判断します：

**新規作成が必要な場合**:
- 新しい画面を追加する
- 既存のUI設計書に該当するものがない

**更新が必要な場合**:
- 既存画面の修正である
- 既存のUI設計書に関連する内容がある

**判断方法**:
1. 実装設計書に記載されている画面名称を確認
2. Glob/Grep で既存のUI設計書を検索
3. 画面の追加 vs 修正 を判断

### 2.3 ファイルパスの決定

新規作成する場合、適切なファイル名を決定します。

**機能仕様書のファイル名**:
- 形式: `{feature-name}.md`
- 例: `task-management-home.md`, `notification-feature.md`
- ケバブケース（kebab-case）を使用

**UI設計書のファイル名**:
- 形式: `{screen-name}-design.md`
- 例: `task-home-screen-design.md`, `notification-settings-design.md`
- ケバブケース（kebab-case）を使用

### 2.4 ユーザー確認（必要な場合）

判断が曖昧な場合や、複数の選択肢がある場合は、ユーザーに確認します。

**確認が必要なケース**:
- 既存の複数の仕様書に影響する可能性がある
- 新規作成と更新のどちらが適切か判断が難しい
- ファイル名の命名に迷う

**確認方法**: AskUserQuestion ツールを使用

## Phase 3: 機能仕様書の作成/更新

### 3.1 機能仕様書の構造

既存の機能仕様書の構造に従います。参考: `docs/specification/features/task-management-home.md`

**必須セクション**:

1. **ドキュメント情報**
   - 作成日
   - 最終更新
   - ステータス（提案中/承認済み/実装済み）
   - 関連ADR（リンク）
   - 画面設計書（リンク）

2. **機能概要**
   - 目的
   - 対象ユーザー
   - 主要機能

3. **ユーザーストーリー**
   - As a ... I want to ... So that ... 形式
   - 受け入れ基準

4. **機能要件**
   - 各機能の詳細仕様
   - 表形式で整理

5. **非機能要件**
   - パフォーマンス
   - ユーザビリティ
   - アクセシビリティ
   - 保守性

6. **データ仕様**
   - データモデルの定義（実装設計書から抽出）
   - 状態管理の仕様
   - データ永続化の方法

7. **UI/UX仕様**
   - 画面設計書への参照
   - 主要コンポーネントの概要

8. **テストシナリオ**
   - ユニットテスト項目
   - 統合テスト項目
   - 手動テスト項目

9. **制約事項**
   - 技術的制約
   - ビジネス的制約

10. **将来の拡張**
    - 短期的な拡張（3-6ヶ月）
    - 中期的な拡張（6-12ヶ月）
    - 長期的な拡張（12ヶ月以降）

11. **参考資料**
    - 関連ドキュメントへのリンク

12. **変更履歴**
    - 日付、バージョン、変更内容、著者

### 3.2 新規作成の場合

Write ツールを使用して、機能仕様書を作成します。

**ファイルパス**: `docs/specification/features/{feature-name}.md`

**情報源**:
- 実装設計書のデータモデル → データ仕様セクション
- 実装設計書のビジネスロジック → 機能要件セクション
- 実装設計書のテスト仕様 → テストシナリオセクション
- 関連ADRの背景と目的 → 機能概要セクション
- 関連ADRの将来の拡張性 → 将来の拡張セクション

### 3.3 更新の場合

Edit ツールを使用して、既存の機能仕様書を更新します。

**更新方針**:
- 既存の内容を尊重し、追加・修正が必要な部分のみを更新
- 変更履歴セクションに更新内容を記録
- 最終更新日を更新

**更新が必要なセクション**:
- 機能要件（新機能の追加）
- データ仕様（新しいモデルやフィールドの追加）
- テストシナリオ（新しいテストケースの追加）
- 変更履歴（必須）

## Phase 4: UI設計書の作成/更新

### 4.1 UI設計書の構造

既存のUI設計書の構造に従います。参考: `docs/specification/ui-design/task-home-screen-design.md`

**必須セクション**:

1. **ドキュメント情報**
   - 作成日
   - 最終更新
   - ステータス（提案中/承認済み/実装済み）
   - デザインシステム（Material Design 3）
   - 関連ドキュメント（機能仕様書、ADRへのリンク）
   - Pencilデザインファイルパス（TODO可）

2. **画面概要**
   - 画面の目的と役割
   - デザインシステムへの言及（MD3準拠）

3. **ワイヤーフレーム**
   - ASCII artで画面構造を表現
   - 各状態のワイヤーフレーム（通常、ローディング、空状態、エラー状態など）

4. **画面要素の詳細**
   - 各UI要素の仕様（Material Design 3コンポーネントを使用）
   - MD3トークン（colorScheme、textTheme）を記載
   - サイズ、パディング、マージンなど

5. **ユーザーインタラクション**
   - タップ、スワイプなどのインタラクションフロー
   - 状態遷移図

6. **状態遷移**
   - 画面の状態遷移図（初期化 → ローディング → データ表示/エラー/空状態）

7. **アニメーション**
   - Duration、Curve、効果の詳細

8. **レスポンシブデザイン**
   - 画面サイズごとの対応
   - 向き（縦/横）の対応

9. **アクセシビリティ**
   - セマンティクスラベル
   - コントラスト比
   - タップ領域

10. **ダークモード対応**
    - MD3トークンの使用を強調
    - ハードコードされた色は使用しない

11. **Pencilデザインファイル**
    - ファイルパス（TODO可）
    - 作成予定の画面リスト

12. **参考資料**
    - Material Design 3へのリンク
    - Flutterドキュメントへのリンク

13. **変更履歴**
    - 日付、バージョン、変更内容、著者

### 4.2 新規作成の場合

Write ツールを使用して、UI設計書を作成します。

**ファイルパス**: `docs/specification/ui-design/{screen-name}-design.md`

**情報源**:
- 実装設計書のUI要件 → 画面要素の詳細セクション
- 実装設計書のテスト仕様 → ユーザーインタラクションセクション
- UIガイドライン → ダークモード対応、アクセシビリティセクション

**重要**: Material Design 3の使用を明記し、具体的なコンポーネント名とトークンを記載してください。

### 4.3 更新の場合

Edit ツールを使用して、既存のUI設計書を更新します。

**更新方針**:
- 既存の内容を尊重し、追加・修正が必要な部分のみを更新
- 変更履歴セクションに更新内容を記録
- 最終更新日を更新

**更新が必要なセクション**:
- 画面要素の詳細（新しいUIコンポーネントの追加）
- ユーザーインタラクション（新しいインタラクションフローの追加）
- 変更履歴（必須）

## Phase 5: Geminiレビュー（必須）

Phase 3とPhase 4で作成/更新した仕様書をGeminiにレビューしてもらいます。

### 5.1 レビューの実行

`mcp__gemini-cli__ask-gemini` ツールを使用してレビューを依頼します。

**重要**: `changeMode: false` を使用してください（仕様書は既に作成済みなので、修正提案のみを受け取る）

**プロンプト例**:

```
以下のドキュメントをレビューしてください。

【機能仕様書】
{機能仕様書の全文をここに挿入}

【UI設計書】
{UI設計書の全文をここに挿入}

【レビュー観点】
1. ドキュメント構造の完全性
   - 必須セクションがすべて含まれているか
   - セクションの順序が適切か
   - 変更履歴が記録されているか

2. ユーザーストーリーの妥当性
   - "As a... I want to... So that..." 形式に従っているか
   - ビジネス価値が明確に示されているか
   - 受け入れ基準が具体的か

3. 機能要件の明確性と網羅性
   - 要件が明確で測定可能か
   - 必要な機能がすべて含まれているか
   - 非機能要件が適切に定義されているか

4. 既存ドキュメントとの整合性
   - 関連ADRとの矛盾がないか
   - 実装設計書との整合性があるか
   - 他の仕様書との用語の一貫性があるか

5. Material Design 3への準拠
   - MD3コンポーネントが正しく指定されているか
   - カラートークン（colorScheme.*）が使用されているか
   - タイポグラフィトークン（textTheme.*）が使用されているか
   - ハードコードされた色値が使われていないか

6. テストシナリオの網羅性
   - 主要な機能がテストでカバーされているか
   - ユニット/統合/手動テストが適切に分類されているか
   - エッジケースが考慮されているか

7. アクセシビリティ要件
   - セマンティクスラベルが定義されているか
   - タップ領域が適切か（44x44pt以上）
   - コントラスト比が考慮されているか

8. ドキュメントの品質
   - 誤字脱字がないか
   - 説明が明確でわかりやすいか
   - 専門用語が適切に使われているか

【出力形式】
各観点について以下の形式で評価してください：

## 観点X: {観点名}
- ✅ 良い点: ...
- ⚠️ 改善提案: ...
- 🔴 問題点: ...（致命的な問題がある場合）

最後に総合評価を記載してください。
```

### 5.2 レビュー結果の分析

Geminiのレビュー結果を分析し、以下に分類します：

**分類基準**:
- 🔴 **致命的な問題**: 必ず修正が必要（例: 必須セクション欠落、MD3違反、矛盾）
- ⚠️ **改善提案**: 修正した方が良い（例: 説明不足、用語の不統一）
- ✅ **良い点**: 問題なし

### 5.3 修正方針の決定

レビュー結果に基づき、修正方針を決定します：

**修正が必要な場合**:
- 🔴 致命的な問題 → 必ず修正（Phase 6で対応）
- ⚠️ 改善提案 → 重要度に応じて修正（Phase 6で対応）

**修正不要な場合**:
- すべて ✅ 良い点のみ → Phase 7へ進む

## Phase 6: レビュー結果反映と修正

### 6.1 修正の実行

Phase 5で指摘された問題点・改善提案を修正します。

**修正方法**:
- Edit ツールを使用して該当箇所を修正
- 致命的な問題を優先的に修正
- 改善提案は重要度の高いものから修正

**修正例**:

```dart
// 🔴 問題: ハードコードされた色が使われている
// 修正前
Container(color: Colors.red)

// 修正後
Container(color: Theme.of(context).colorScheme.error)
```

### 6.2 修正内容の記録

変更履歴セクションに修正内容を記録します（該当する場合）。

**記録形式**:
```markdown
| 日付 | バージョン | 変更内容 | 著者 |
|------|-----------|----------|------|
| {日付} | 1.1 | Geminiレビュー結果を反映（MD3トークン使用、セクション追加） | Claude Code |
```

### 6.3 修正完了確認

すべての致命的な問題が修正されたことを確認します。

- [ ] 🔴 致命的な問題がすべて修正された
- [ ] ⚠️ 重要な改善提案が反映された
- [ ] 変更履歴が更新された（該当する場合）

## Phase 7: 最終確認とユーザー報告

### 7.1 作成/更新ファイルのリスト化

作成または更新したファイルをリスト化します。

**形式**:
```
✅ 機能仕様書: docs/specification/features/{feature-name}.md（新規作成/更新）
✅ UI設計書: docs/specification/ui-design/{screen-name}-design.md（新規作成/更新）
```

### 7.2 内容の最終確認

以下の点を確認します：

- [ ] 機能仕様書のすべての必須セクションが含まれているか
- [ ] UI設計書のすべての必須セクションが含まれているか
- [ ] 関連ドキュメントへのリンクが正しいか
- [ ] Material Design 3への準拠が明記されているか
- [ ] 変更履歴が記録されているか
- [ ] 相対パスが使用されているか（絶対パスは不可）
- [ ] Geminiレビューの指摘事項が反映されているか

以下の形式でユーザーに報告します。
